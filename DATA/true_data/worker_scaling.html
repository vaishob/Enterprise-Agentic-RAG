Scaling Test Workers Across CI Runners

A single machine only scales a Playwright suite so far \u2014 workers are capped by CPU cores, and browsers are memory-hungry. Beyond a certain suite size, the only way to keep run time flat is to scale out across multiple CI runners, not just up within one.

Two axes of scaling

AxisMechanismBound by
Vertical (within a machine)workers config / --workersCPU cores, available memory
Horizontal (across machines)--shard=x/y + CI matrixNumber of parallel runner jobs your CI plan allows

Horizontal scaling with sharding

Sharding splits the resolved test list into equal slices by index, letting each CI runner claim one slice independently:

# .github/workflows/e2e.yml
strategy:
  matrix:
    shardIndex: [1, 2, 3, 4]
    shardTotal: [4]
steps:
  - run: npx playwright test --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}

Each matrix entry is a fully independent job \u2014 its own runner, its own container, its own worker pool sized by that runner's CPU count. Scaling from 4 to 8 shards is a one-line change to the matrix, with no change to the test code itself.

Containerizing the worker

Official Playwright Docker images bundle matching browser binaries with the npm package version, which avoids the most common source of CI flakiness: a browser binary that's silently out of sync with the test runner.

FROM mcr.microsoft.com/playwright:v1.48.0-jammy
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["npx", "playwright", "test", "--shard=${SHARD_INDEX}/${SHARD_TOTAL}"]
Pin the image tag to the exact Playwright version in package.json. A mismatched browser/runner version pair is a frequent cause of tests that pass locally and fail only in CI.

Sizing a worker container

Each headless Chromium/WebKit/Firefox instance typically needs on the order of 300\u2013500MB of memory under moderate page weight, so a container running N workers should budget roughly N \u00d7 500MB plus headroom for the Node.js process itself. Under-provisioning memory shows up as workers being silently OOM-killed rather than as a clear test failure, which makes it a disproportionately confusing failure mode to debug from logs alone.

Dynamic runner pools

Self-hosted CI runner pools (GitHub Actions runner groups, GitLab autoscaling runners, Buildkite elastic stacks) can scale the number of available runner machines up and down based on queue depth, rather than keeping a fixed pool warm at all times:

  • Queue depth crosses a threshold \u2192 the autoscaler provisions additional runner instances
  • New instances register with the CI control plane and pick up queued shard jobs
  • Once the queue drains, idle instances are terminated after a cool-down window
Autoscaled runners are usually ephemeral \u2014 don't rely on local disk state (cached browsers, node_modules) surviving between runs unless the pool explicitly supports a persistent cache layer.

Cost vs. speed tradeoffs

More shards reduce wall-clock time close to linearly until per-job fixed overhead (checkout, dependency install, browser download) starts to dominate. Past that point, additional shards mostly add cost without meaningfully shortening the run \u2014 the practical ceiling for most suites sits where fixed per-job overhead reaches roughly 15\u201320% of that shard's total run time.

ShardsApprox. wall timeRunner-minutes billedNotes

The table illustrates the general shape rather than fixed numbers \u2014 the actual crossover point depends heavily on how expensive checkout and dependency install are relative to the suite itself.

Caching browser binaries

Downloading Chromium, WebKit, and Firefox on every job is one of the largest fixed costs in a scaled-out CI setup. Caching the browser binary directory keyed off the installed Playwright version avoids re-downloading them on every shard:

- uses: actions/cache@v4
  id: playwright-cache
  with:
    path: ~/.cache/ms-playwright
    key: playwright-${{ runner.os }}-${{ hashFiles('package-lock.json') }}

- run: npx playwright install --with-deps
  if: steps.playwright-cache.outputs.cache-hit != 'true'

Skipping the install step entirely on a cache hit \u2014 rather than always running playwright install \u2014 is what actually saves time; the cache alone does nothing if the install command still runs unconditionally afterward.

Monitoring worker utilization

Once a suite is scaled across several shards and workers, the more useful signal is usually not "did it pass" but "how efficiently did it use the machines it was given." Worth tracking over time:

  • Per-worker idle time \u2014 large gaps suggest test files are unevenly sized and would benefit from re-balancing (Playwright's default distribution is by file count, not by historical duration)
  • Peak memory per container \u2014 approaching the container's limit is an early warning sign for OOM-killed workers before they start failing outright
  • Shard finish-time spread \u2014 if one shard reliably finishes far later than the others, the test list isn't being split evenly in practice and a duration-aware split (or manual re-grouping) is worth investigating

Example resource limits (docker-compose)

services:
  playwright-worker:
    image: mcr.microsoft.com/playwright:v1.48.0-jammy
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2g
    environment:
      - PLAYWRIGHT_WORKERS=4
    command: npx playwright test --shard=${SHARD_INDEX}/${SHARD_TOTAL}

As a starting point, budgeting roughly 0.5 CPU and 500MB of memory per worker keeps most suites comfortably within limits; suites with particularly heavy pages (large SPAs, video, canvas-heavy UI) should budget higher and verify against observed peak memory rather than this rule of thumb alone.

Headless rendering and GPU considerations

Headless Chromium, WebKit, and Firefox all render without a physical display, but "headless" doesn't mean "no rendering work happens" \u2014 layout, paint, and compositing still run in software unless a GPU is explicitly made available to the container. On most CI runners there is no GPU at all, which is usually fine for functional testing but has two practical consequences worth planning for:

  • Visual/screenshot tests are more sensitive to the renderer. Software rendering can produce subtly different anti-aliasing or font hinting than a GPU-backed render on a developer's machine, which is why screenshot baselines are usually generated inside the same container image the CI job uses, not captured locally.
  • CPU cost per page goes up without a GPU. Pages with heavy CSS animation, canvas, or WebGL content shift rendering cost onto the CPU cores that workers are already competing for, which is one more reason worker count and container CPU limits need to be tuned together rather than independently.

Some managed CI platforms do expose GPU-backed runners for exactly this reason, but they are a deliberate opt-in for suites where render fidelity or GPU-dependent behavior actually matters, not a default choice.

A worked scaling example

To make the tradeoffs concrete: consider a suite of 600 test files with an average of 4 seconds per file, giving roughly 40 minutes of sequential work.

ConfigurationWorkers per shardShardsApprox. wall time
Single runner, default workers41~10 min
Single runner, maxed workers81~6 min (memory-bound past this point)
Matrix of runners, moderate sharding44~3 min
Matrix of runners, aggressive sharding28~2.5 min, higher total runner-minutes

The jump from 1 shard to 4 shards gives the largest practical improvement for the least added cost; going from 4 to 8 shards buys a smaller further reduction while roughly doubling billed runner-minutes \u2014 the same diminishing-returns pattern shows up regardless of the specific suite size or per-test duration.

Frequently asked questions

Does adding more shards always reduce wall-clock time?

Only up to the point where fixed per-job overhead (checkout, install, browser cache restore) stops being negligible relative to the shard's share of the suite. Beyond that point, more shards mostly add cost.

Should shard count match worker count?

No \u2014 they solve different problems. Workers parallelize within one machine's CPU budget; shards parallelize across separate machines entirely. A well-tuned setup usually sets workers close to a single runner's core count, and separately tunes shard count based on total suite size and acceptable wall-clock time.

Is it worth building a custom autoscaler instead of using vendor-hosted runners?

Usually only once vendor-hosted runner limits or cost at your actual concurrency level become a real constraint \u2014 for most suites the operational cost of running and monitoring a self-hosted autoscaling pool outweighs the savings until CI usage reaches a significant, sustained scale.

Provider-specific autoscaling configuration

The concept \u2014 scale runner count with queue depth, scale back down on idle \u2014 is consistent across CI providers, but the configuration surface differs enough to be worth comparing directly.

GitHub Actions (self-hosted, autoscaling runner scale sets)

# values.yaml for actions-runner-controller
minRunners: 0
maxRunners: 20
scaleDownDelaySecondsAfterScaleOut: 300
template:
  spec:
    containers:
      - name: runner
        resources:
          requests: { cpu: "2", memory: "4Gi" }
          limits:   { cpu: "2", memory: "4Gi" }

The controller watches the Actions job queue directly and provisions ephemeral runner pods on demand; each pod runs exactly one job and is discarded afterward, which keeps the pool naturally clean of stale state between runs.

GitLab CI (autoscaling Docker Machine executor)

[[runners]]
  limit = 20
  [runners.machine]
    IdleCount = 1
    IdleTime = 600
    MaxBuilds = 1
    MachineDriver = "amazonec2"

MaxBuilds = 1 is the equivalent guarantee to GitHub's ephemeral pods \u2014 each provisioned machine handles exactly one job before being torn down, trading a small provisioning-time cost for a guarantee that no state leaks between jobs.

Buildkite (elastic CI stack)

MIN_SIZE: 0
MAX_SIZE: 30
SCALE_IN_IDLE_PERIOD: 300
SCALE_IN_COOLDOWN_PERIOD: 60

Buildkite's elastic stack watches its own job queue via CloudWatch metrics and adjusts an underlying EC2 auto-scaling group directly, which makes tuning scale-in aggressiveness a matter of adjusting cooldown periods rather than pool size directly.

Capacity planning checklist

Before changing shard or worker counts on an existing pipeline, it's worth establishing a baseline rather than tuning by trial and error under pressure during a slow release week:

  • Record current wall-clock time, shard count, and worker count together \u2014 changing one without recording the others makes later comparisons meaningless.
  • Capture peak memory per worker over at least a week of runs, not a single sample \u2014 memory use varies with which specific tests land on which worker.
  • Separate "suite got slower" from "infrastructure got slower" by checking whether average per-test duration changed, or only the number of tests changed.
  • Re-evaluate shard count whenever suite size grows by roughly 30\u201340% \u2014 the previous split point was tuned for a different total, and small suites that grow gradually often end up several tunings behind where they should be.
  • Treat any autoscaling minimum-runner setting above zero as a standing cost, not a one-time decision \u2014 idle warm capacity is billed the same as active capacity on most platforms.

None of this replaces measuring your own pipeline directly \u2014 the numbers throughout this document illustrate the shape of the tradeoffs, not values to copy verbatim into a specific CI configuration.
