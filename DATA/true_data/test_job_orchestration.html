Test Job Orchestration

Playwright Test does not treat a run as one flat list of specs. It groups work into projects, filters that work with tags and grep patterns, and sequences it with dependencies \u2014 together these are what let a single test suite behave like several distinct "jobs" without duplicating code.

Projects: the unit of orchestration

A project in playwright.config.ts is a named configuration \u2014 browser, viewport, base URL, storage state \u2014 that a subset of your tests will run under. Most teams define one project per browser engine, but projects are just as useful for splitting environments or test categories:

export default defineConfig({
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    { name: 'mobile-smoke', use: { ...devices['iPhone 13'] }, testMatch: /smoke\/.*\.spec\.ts/ },
  ],
});

Running npx playwright test --project=chromium executes only that project's slice of the suite \u2014 this is the mechanism CI matrices use to split a run into independent jobs that can be scheduled on separate machines.

Filtering work: tags and grep

Rather than maintaining separate spec files per job, tests can be annotated and filtered at run time:

test('checkout completes with saved card @smoke @regression', async ({ page }) => {
  // ...
});
# Run only smoke-tagged tests
npx playwright test --grep @smoke

# Run everything except slow/flaky-quarantined tests
npx playwright test --grep-invert @quarantine
FlagEffect
--grepInclude tests whose title matches the pattern or tag
--grep-invertExclude tests whose title matches the pattern or tag
--projectRestrict the run to one or more named projects
--shardSplit the resolved test list across N machines by index

Dependencies between projects

Some jobs genuinely need to run before others \u2014 authentication being the most common case. A dependencies field turns one project into a prerequisite for another, and Playwright's dispatcher will not start the dependent project's workers until the dependency project has finished successfully:

projects: [
  { name: 'setup', testMatch: /global\.setup\.ts/ },
  { name: 'chromium', use: { storageState: 'playwright/.auth/user.json' }, dependencies: ['setup'] },
]
Dependencies are resolved once per run, not once per worker \u2014 the saved storageState is reused by every worker in the dependent project, so authentication only happens a single time even across dozens of parallel workers.

Global setup and teardown

For orchestration concerns that sit above any single project \u2014 seeding a database, starting a mock server, tearing down shared fixtures \u2014 globalSetup and globalTeardown run once for the entire invocation, regardless of how many projects or shards are involved:

export default defineConfig({
  globalSetup: require.resolve('./global-setup.ts'),
  globalTeardown: require.resolve('./global-teardown.ts'),
});

Composing it into a CI matrix

In practice, orchestration in CI usually combines all three mechanisms: a matrix strategy iterates over projects (or shards), each matrix entry runs --project and/or --shard to claim its slice, and a final job waits on all of them before merging reports. The result is a set of independent, resumable "jobs" carved out of one shared test definition, rather than one long serial run.

jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        project: [chromium, firefox, webkit]
        shardIndex: [1, 2]
        shardTotal: [2]
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: >
          npx playwright test
          --project=${{ matrix.project }}
          --shard=${{ matrix.shardIndex }}/${{ matrix.shardTotal }}
      - uses: actions/upload-artifact@v4
        with:
          name: blob-report-${{ matrix.project }}-${{ matrix.shardIndex }}
          path: blob-report

  merge-reports:
    needs: [e2e]
    steps:
      - uses: actions/download-artifact@v4
      - run: npx playwright merge-reports --reporter=html ./all-blob-reports

This single matrix expands into six independent jobs (three projects × two shards), each a self-contained "unit of work" that can fail, retry, or be re-run in isolation without touching the other five.

Annotations for job-level control

Beyond tags, Playwright supports annotations that change how a test participates in a run entirely, which is often a cleaner way to carve out a "job" than maintaining a separate spec file:

AnnotationEffect
test.skip(condition, reason)Skip a test conditionally \u2014 e.g. skip a mobile-only test on desktop projects
test.fixme(condition, reason)Mark a known-broken test as expected to fail, without deleting it
test.slow()Triple the default timeout for a test known to be legitimately slow
test.describe.configure({ retries: 0 })Override retries for one group, independent of the global config
test.describe('checkout', () => {
  test.describe.configure({ retries: 0 }); // this group must never mask flakes

  test('rejects an expired card', async ({ page }) => {
    test.skip(process.env.PAYMENT_SANDBOX !== 'true', 'requires sandbox payment provider');
    // ...
  });
});

Structuring a test into sub-steps

test.step() doesn't change scheduling, but it gives long tests a job-like internal structure in the report \u2014 each step shows up as a collapsible node with its own timing, which makes a single 40-line test readable as a sequence of named phases rather than one flat block:

test('completes a full purchase', async ({ page }) => {
  await test.step('add item to cart', async () => { ... });
  await test.step('apply promo code', async () => { ... });
  await test.step('submit payment', async () => { ... });
});

Reading job identity at runtime

Inside a test, testInfo() exposes exactly which "job" a given execution belongs to \u2014 useful for routing logs, naming screenshots, or tagging any external system a test touches with the run that produced it:

test('example', async ({ page }, testInfo) => {
  console.log(testInfo.project.name);   // e.g. "chromium"
  console.log(testInfo.workerIndex);    // e.g. 2
  console.log(testInfo.retry);          // 0 on first attempt, 1+ on retries
});
Combining project name, shard index, and worker index gives every single test execution a fully unique coordinate \u2014 useful when correlating a failure back to the exact CI job and machine that produced it.

Designing a tag taxonomy

Tags are just substrings in a test title, so nothing stops a team from inventing dozens of one-off tags that quietly stop meaning anything after a few months. A small, deliberate taxonomy tends to age better than an organic one:

TagIntended jobTypical trigger
@smokeFast confidence checkEvery push, pre-merge
@regressionFull functional coverageNightly, pre-release
@visualScreenshot comparison suiteNightly, isolated job (different infra needs)
@quarantineKnown-flaky, excluded from gatingNever blocks merges; tracked separately

Two properties matter more than the exact names chosen: every tag should map to a specific CI job that consumes it, and a test should never need more than two or three tags before the taxonomy itself needs revisiting.

Grep patterns beyond a single tag

--grep accepts a regular expression, not just a literal tag, which allows more precise slices of a suite to be carved into a job without adding new tags:

# Only checkout-related smoke tests
npx playwright test --grep "@smoke.*checkout|checkout.*@smoke"

# Everything in the "billing" describe block
npx playwright test --grep "^billing "

# Skip anything tagged either quarantine or manual-only
npx playwright test --grep-invert "@quarantine|@manual"

Because the pattern matches against the full test title \u2014 including any parent describe blocks \u2014 nesting related tests inside a named describe is often enough to carve out a job-sized slice without any tagging at all.

Anti-patterns to avoid

  • Duplicating a spec file per environment. A checkout.staging.spec.ts and checkout.prod.spec.ts that differ only in base URL are better expressed as one spec file and two projects with different use.baseURL values.
  • Encoding job identity in the test title alone. Titles are for humans reading a report; use testInfo, tags, and project names \u2014 which are queryable \u2014 rather than parsing conventions out of a string.
  • One giant project with conditional logic inside every test. If half your tests branch on if (isMobile) { ... } else { ... }, that's usually a sign the branch should be a second project instead.

Timeouts at every level

A "job" hanging indefinitely is often worse than one failing fast, so Playwright layers timeouts at several scopes rather than relying on one global value:

ScopeConfig keyTypical default
Per testtimeout30s
Per assertionexpect.timeout5s
Whole run (all projects/shards combined)globalTimeoutunset (no cap)
Global setupglobalSetupTimeout (via CLI wrapper)inherits per-test default

Setting globalTimeout in CI is a common safeguard on top of per-test timeouts: it caps how long an entire job can occupy a CI runner even if some unexpected condition (a hung browser, a stuck network request) causes many individual per-test timeouts to chain together longer than expected.

export default defineConfig({
  timeout: 30_000,
  globalTimeout: 60 * 60 * 1000, // hard stop at 1 hour for the whole run
  expect: { timeout: 5_000 },
});

Quick reference: choosing a mechanism

A rough decision guide for which orchestration tool fits a given need:

  • Different browser/device/environment → project
  • Subset of an existing suite, run on demand → tag + grep
  • One project must run before another → dependencies
  • Suite too large for one machine → sharding
  • Setup/teardown shared by the whole run → globalSetup / globalTeardown
